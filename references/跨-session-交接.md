# 跨 session 交接：回頭修改上游／接續下游

所有「上游產出 → 下游使用」的鏈都適用：boss-design → boss-demo → plan-dept14-writer、cannon-wing → cannon-parts／cannon-storyboard、pet-evolution → pet-parts、weapon-design → weapon-parts、game-prototype → game-develop → product-planning（反寫）。這些常在不同 session、不同天做；下游審稿時發現要改上游（例：企劃審稿帶出 demo 要改），照這份交接，不臨場發明格式（組員建議，2026-10-15；來源是一次 Boss 企劃審稿→demo 修改→回來補企劃的實跑）。

## 一、決定先寫進規格正本，標日期

1. 下游 session 討論出的每一個決定（新規則、改數值、改表演），**先寫進該線的規格正本**（Boss 線＝demo 的規格彙整檔；生圖線＝mini 企劃或 Notion 企劃頁；遊戲線＝`GAME_SPEC.md`），開一節「§0 新決定（YYYY-MM-DD）」，一條一個決定、附理由。
2. 不要只留在對話裡、也不要只寫在交接清單——交接清單會丟，規格正本會留。

## 二、交接清單分兩段

寫成一個檔（`交接_YYYYMMDD.md`，放該專案資料夾），只有兩段：

```
## 上游要做（給 <上游 skill> session）
- [ ] 改 X：依規格 §0 第 n 條 …（檔案／位置）
- [ ] 改 Y：…
不要動：企劃頁、下游的檔（列出來）

## 做完回下游要做（給 <下游 skill> session）
- [ ] 驗收：檔案時間晚於 YYYY-MM-DD HH:MM、搜關鍵字「…」、看圖第 n 格
- [ ] 補企劃 §…／重截分鏡／重跑 QA
```

- 「上游要做」只列上游該動的檔，並**明列不准動的東西**——上游 session 越界改企劃是最常見的事故。
- 「做完回下游要做」第一條永遠是驗收，不是直接接著做。

## 三、貼給對方 session 的一段話

交接清單寫好後，產出一段可直接貼的開場（≤10 行）：這是哪條線、規格正本在哪、交接清單在哪、只做「上游要做」那段、做完更新規格正本並回報。不附整份規格，讓對方自己讀正本。

## 四、上游做完：更新規格正本，回報

上游 session 改完後：§0 的每條決定標「已做（日期）」或「未做＋原因」；改到的檔案列路徑；分享版／輸出檔重新打包。不改企劃、不替下游補文件。

## 五、下游接手前先驗收

回到下游 session，接手前照「做完回下游要做」的驗收條逐一確認：檔案時間、關鍵字、看圖（分鏡格、截圖）、數值對規格 §0。驗收不過就退回上游，不自己改上游的檔。驗收過了才補企劃、重截分鏡、重跑 QA。

## 六、不這樣做會怎樣（前科）

- 決定只留在對話 → 下一個 session 讀不到，上游照舊版改。
- 交接清單沒分段 → 上游 session 順手把企劃也改了，兩邊版本打架。
- 接手不驗收 → 企劃補了舊 demo 的分鏡。
