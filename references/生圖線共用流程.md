# 生圖線共用流程（魚樂園十支）

> 適用：`boss-design`、`boss-props`、`boss-scene`、`cannon-wing`、`cannon-parts`、`cannon-storyboard`、`pet-evolution`、`pet-parts`、`weapon-design`、`weapon-parts`。
> 這份管**魚線工作流程**的共用段：前置需求、讀企劃、全程規則、從零發想的提案與 mini 企劃拍板、挑圖、檢視與交付、接續下游。各 SKILL.md 只留該支獨有的差異（讀哪本之書、法則檔與節號、提案要給的欄位、mini 企劃模板、常見失敗、下游清單），在動作發生的那一步指回這裡。
> **產圖層面**的問題（配額與素材表、算圖中斷、憑證到期換季、平台偶發異常、模型固定偏誤、注意力零和）在同層的 `image-studio-共用須知.md`，兩份不重複。

## 一、前置需求

1. **image-studio 憑證**：`~/.config/image-studio/credentials.json`。401 時見 kit `references/image-studio-共用須知.md`〈憑證〉（Claude 照該節換季流程自己換，不提前換；本機沒裝過走〈首裝流程〉）
2. **Notion 讀取權**：該線的之書（四部）——魚類之書（Boss 線）、道具之書（炮台翅膀、寵物、武具線）、功能之書〈武具系統〉（武具線另讀），各 SKILL.md 寫自己讀哪本。自己的四部（pm4）憑證在本機，`fetch_plan.py` 自動取，不用傳任何 key、不要問使用者；沒有或過期照 `plan-dept14-writer/references/notion-access.md` §3 協助安裝／換新
   ⚠️ **Notion 一律走部門 proxy＋REST，不走 MCP**（MCP 已移除）。憑證值不印出、不寫進任何檔案
3. **Python 套件**：Pillow（各 skill 另需的套件——例如 `cannon-wing` 的 numpy——寫在自己的前置需求）

## 二、讀企劃（`fetch_plan.py`）

- 讀企劃：`~/.claude/skills/art-request-sheet/scripts/fetch_plan.py`（全 kit 唯一一份；boss×3、cannon-wing、pet×2、weapon×2 共 8 支引用，`--list bosses/pets/cannons/wings/weapons` 列候選）。讀單一企劃頁（文字＋圖片）一律用這支共用腳本，不用傳任何 key：

  ```sh
  python ~/.claude/skills/art-request-sheet/scripts/fetch_plan.py <page_id> _工作暫存/<物件名>
  ```

- 產出 `plan.md`（企劃全文，紅字／灰綠底／刪除線標記保留）與 `NN_<圖名>.png`（企劃圖與影片，簽名 URL 約 5 分鐘失效，腳本當下就下載）；`plan.md` 裡 `[image …]` 那行就是對應檔名，直接 Read 即可。表格內容（WID、關聯道具）已展開成一列一行
- **企劃圖要實際 Read 來看**——文字與圖常常不一致；不一致時列給使用者，**問要照文字還是照圖**。企劃圖常混著 UI mockup、漁場背景、佔位角色，要認清哪張才是定稿
- 要自己下別的 database query（例如加稀有度 filter）的寫法與禁忌（不要自己讀 credentials.json、不要用 PowerShell 打 REST）見 `cannon-wing/SKILL.md` Step 1

## 三、全程規則（十支共用）

- **每輪至少算 2 張**：平台會偶發異常（貼紙風、底色卡、底座、加文字、產出與企劃不符），對策是重抽不是改提示詞
- **不修改任何既有企劃**：發現的錯字、矛盾、缺漏，列給使用者看即可。**主動點出企劃問題**：企劃缺造型描述、階段不全、用詞不一致、文字與圖不符、內部矛盾時直接講，不要自行補完後默默帶過
- **中間產物進 `_工作暫存/`**（已 gitignore），不進使用者的下載資料夾；定稿才輸出到使用者指定位置。**未上線的設計圖不進 repo**（kit 是公開 repo）
- **有企劃的一次全部盤點、派出去產，不要一件一件問**；只有企劃沒寫到的才逐項詢問規格
- **法則優先**：產圖前後都對照該 skill 的法則／規格檔，交付前逐條跑它的驗收清單（檔名與節號各 SKILL.md 寫）

## 四、從零發想（模式 B）：先提案，mini 企劃拍板才算圖

⚠️ **提案與拍板不可跳過**，沒等使用者拍板不算圖。模式 B 產出 mini 企劃並經使用者拍板後，接回該 skill 的「組提示詞」那一步；之後與模式 A 共用。

- **B1 收集方向**：問使用者（問哪幾件各 SKILL.md 列），全部可選，沒給就自由發揮
- **B2 避開既有題材**：發想前先重撈該線清單（`fetch_plan.py --list <bosses|pets|cannons|wings|weapons>`），對照該 skill `參考素材索引.md` 的已用題材，避免撞題與撞名；另避開其他線已用的動物造型
- **B3 提案**：發想 **2–3 個差異明顯**的方向讓使用者挑，並**明講他可以完全不選、直接自己給主題**——不要把他框在提案裡。每案要給的欄位各 SKILL.md 列；每案都要有**設計理由（2–3 句）**：為什麼選這個題材（跟既有物件的區隔、跟捕魚主題的關係）。**沒有理由的提案不交**——使用者要靠理由判斷，不是只看名字挑
- **B4 產 mini 企劃**：照該之書的結構，**只寫產圖需要的部分**（欄位模板各 SKILL.md 列）；存成 `_工作暫存/企劃_<名稱>_v1.md`，給使用者閱讀。**逐條對照該 skill 法則檢查**後才交出
- **B5 修訂迴圈**：使用者提調整 → **重出一整份完整企劃**（版本號 +1），不要只給差異片段。確認滿意才進組提示詞。產圖後若使用者又改了設計，記得把改動折回企劃檔，避免圖與企劃脫節

## 五、挑圖

**⚠️ 一定要看完所有候選圖，並從中挑最好的一張。** 只看第一張就評斷等於放棄了 `--count` 的意義；**兩張可能都符合規格，但有優劣**——「符合規格」與「畫得好」是兩件事，規格只是門檻。

| 情況 | 處置 |
|---|---|
| 有一張以上正確 | **全部看完，挑最好的**，不要改提示詞 |
| 兩張都錯在同一點 | 才是提示詞或規格的問題，回「組提示詞」那一步修 |
| 兩張錯在不同點 | 隨機變異，重抽 |

逐張 Read，對照該 skill 法則／規格檔的驗收清單；該 skill 常見的失敗與處置各 SKILL.md 列。平台異常（底座、底色卡、貼紙風、文字、場景）→ 重抽，常見異常見 `image-studio-共用須知.md`。

## 六、檢視、交付、接續下游

1. 把候選圖複製到使用者看得到的資料夾，用 `explorer.exe` 開給他看
2. **自己先逐條跑驗收清單**，主動回報哪張好、好在哪、還差什麼，不要等使用者挑
3. 使用者提調整 → 改企劃或提示詞回「組提示詞」那一步（後製參數有問題就回該後製步驟）
4. 定稿圖輸出到使用者指定位置，附最終提示詞
5. 這次暴露了新規則或前科 → 回寫該 skill 的法則／規格檔（前科節）或 `prompt模板.md`（落點各 SKILL.md 寫）
6. **主動接續下游**：使用者確認定稿後，主動問要不要接著做下游（下游清單各 SKILL.md 列）。**全部以這裡的定稿為參考圖延伸**，不重新發想造型與配色——所以一定要等定稿才做。先讀企劃盤點：**企劃有寫的一次全部派出去產**，不要一件一件問；只有企劃沒寫到的才逐項詢問。從零發想的物件沒有企劃：依 mini 企劃提出下游清單與內容，使用者拍板後派出

### 下游審稿要回頭改上游（例：配件審到要改定稿、分鏡審到要改外觀）

照 `跨-session-交接.md`（同目錄）：決定先寫進規格正本標日期 → 交接清單分「上游要做」「做完回下游要做」 → 上游改完更新正本 → 下游接手前先驗收（檔案時間、關鍵字、看圖），不臨場發明格式。
