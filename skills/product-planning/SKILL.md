# 產品企劃工作流

> **執行角色：企劃**——關注玩家體驗、核心循環、商業目標、可驗證的假設；產出後主動切**工程**與**數值**視角各挑一輪風險再交付。

## 啟動判斷(先分流再動工)

依使用者輸入判斷模式,不確定就問一句:

- **A 從零**:只有想法/口述需求,沒有實作與現成文件
- **B 反寫**:給了 demo(HTML/專案資料夾/GAME_SPEC),要產對應企劃書
- **C 審修**:給了寫好的企劃檔,要檢查修正

## 共通規則(三模式都適用)

1. **先問參考範本**:「有沒有要照的範本檔?」有 → 結構完全照範本;沒有 → 用下方內建骨架
2. **語言**:內文繁體中文;專業名詞可英文(RTP、LTV、DAU);玩家看得到的 UI 字串一律繁中
3. **Mermaid**:操作/系統流程一律附 Mermaid(必要時 2–3 組:玩家操作流、系統判定流、異常/防呆流);節點文字精簡,一張圖不超過 12 節點,複雜就拆圖
4. **輸出**:單一 Markdown 檔,格式可直接貼進 Notion(標題層級、表格、mermaid code block);存檔位置問使用者或放專案資料夾
5. **數值表**必為 Markdown table,含欄位:項目/數值/依據(拍腦袋的標「暫定」)
6. 產出後主動提議品管:機制數值多 → 派 game-balance-auditor;有對應實作 → 派 planning-doc-auditor 對照
7. 有部門專屬企劃 skill(house style)時優先走它;本 skill 只在無範本或跨部門時使用

## 內建骨架(無範本時)

```
# <企劃名>(vX.X / 日期)
1. 目標與背景 — 要解決什麼、成功指標(具體數字)
2. 對象與體驗 — 給誰玩/用、核心體驗一句話
3. 機制說明 — 規則逐條,含觸發條件與邊界
4. 數值設定 — 表格(項目/數值/依據)
5. 介面與分鏡 — 畫面清單、關鍵分鏡秒數
6. 流程圖 — Mermaid 2–3 組
7. 驗收條件 — 可勾選的 checklist
8. 風險與開放問題 — 待拍板事項明列
```

## 模式 A:從零寫

1. **缺口訪談**:對照骨架逐段盤點使用者已講/沒講的,一次列出所有缺口問題(不要一題一題擠牙膏);使用者說「先假設」的段落自行補上並標「暫定」
2. 產出完整企劃,暫定項集中列在 §8 開放問題
3. 摘要回報:哪些是使用者拍板的、哪些是暫定的

## 模式 B:從 demo 反寫

1. 讀實作(HTML 原始碼、GAME_SPEC.md——格式見 `game-develop/templates/GAME_SPEC.template.md`、專案 memory),反推:機制規則、數值(從 code 常數萃取,標來源行號)、畫面與分鏡(從 UI 結構)
2. 實作已存在的內容標「已實作驗證」;企劃需要但 demo 沒做的(營運面、防呆、異常流)補寫並標「企劃補充,未實作」
3. 數值一律以 code 為準,不憑印象;讀不到的問使用者
4. 產出後建議派 planning-doc-auditor 反向核對一次(企劃 vs 實作雙向一致)

## 模式 C:審修現成企劃

**使用者指定單項(「只補流程圖」「只抓錯字」「只查邏輯」)→ 只動手做該項**;但讀文件過程順帶看到的其他問題(錯字、邏輯矛盾)——**尤其畫流程圖本來就得先讀懂邏輯——結尾用一段「另外注意到」列出提醒,不動手改**,使用者點頭才處理。沒指定單項才依序跑三層,產出「修正後全文＋審查報告」兩件套:

1. **錯字與用語**:錯別字、全半形混用、同一名詞多種寫法(例:同文件混用「玩家/使用者」)→ **直接改**,報告列 diff 摘要
2. **邏輯檢查**:數值自洽(表內數字加總/機率總和/上下限矛盾)、流程斷點(有進入沒出口的狀態)、段落缺漏(對照骨架找漏段)、規則衝突(兩條規則同情境不同結論)→ **不直接改**,列問題清單＋建議修法,使用者拍板才動
3. **補 Mermaid**:文中用文字描述流程但沒圖的段落,畫出對應流程圖插入;既有的圖檢查與文字描述是否一致
4. 報告格式:🔴 邏輯問題(需拍板)/🟡 建議優化/✅ 已直接修正(錯字類)

## 鐵則

- 不虛構數值:沒依據的一律標「暫定」,不要編一個看起來合理的數字
- 模式 C 的邏輯問題**只列不改**,決定權在使用者
- 不寫入個資與內部機密;企劃內容視為內部文件,不主動外發
