# 異常回報、優化建議與收單（issue-triage）

> **執行角色：數值／QA**——關注可重現性、根因證據、影響鏈；回報模式**只觀察不修改**，收單模式修完切**工程**視角複核測試覆蓋。

## 適用範圍

不限 starter kit——**secretary-kit（Slack 秘書）與任何 kit 發佈的工具異常都走同一套**；環境段的版本 hash 取對應 repo（秘書：`git -C %USERPROFILE%\secretary-kit log --oneline -1`）。

## 模式判斷

- 使用者自己遇到異常、說「回報」「幫我看這個 bug」→ **A 回報模式**
- 沒壞、但覺得某支 skill 不順手：流程多一步、觸發詞叫不到、輸出格式不合用、想加選項／功能 → **C 建議模式**（整理時若查 SKILL.md 發現現況跟文件寫的規格對不上，仍出建議單，在「影響範圍」註明「現況與文件規格不符，疑為異常」，由維護者判定，不必改走 A 重做）
- 使用者貼來別人寫的異常回報或建議單、說「處理／收單」→ **B 收單模式**（建議單走 B 末段的簡化路徑）
- 自己（Claude）在執行中發現 kit 工具異常 → 先以 A 的格式記錄，問使用者要自修（轉 B）還是回報給維護者
- 使用者說「kit 使用回顧」、或維護者請大家回顧近期使用 → **D 使用回顧模式**
- 使用 kit skill 的任務收尾時 → 套「收尾自檢」（見文末），踩雷才出單

## A. 回報模式（產出標準回報，不動手修）

**鐵則：只觀察、記錄、驗證，不修改任何 kit 檔案**——junction 裝的 skill 改了會與 kit 版本衝突，之後升級會蓋掉或打架。臨時 workaround 寫在回報的「暫時繞法」段，不寫進 kit 檔。

依序收集，缺一項就補做一步：

1. **環境**：OS／Python 或 Node 版本／kit 版本（`git -C %USERPROFILE%\starter-kit log --oneline -1` 的 hash）
2. **最小重現**：把觸發條件縮到最小（一條指令、一個 prompt、一個輸入檔），確認重現至少 2 次；不能穩定重現就寫出現機率與已試次數
3. **根因**（盡力而為）：讀相關原始碼，指出可疑行號與判斷邏輯；查得到「為什麼會漏」最好（例：這種回應形態剛好通過上一層檢查）
4. **實際影響鏈**：這個 bug 往下游會造成什麼（靜默壞資料＞報錯中斷＞外觀問題），哪種使用情境風險最高
5. **建議修法**：給方向即可，並**尊重原設計約束**（零依賴、單檔、junction 架構），不建議引入新依賴的修法除非別無他法
6. **對照案例**（有就寫）：kit 內有沒有修過同類問題，本次是不是它的對稱面

**輸出格式**（固定，交給使用者轉發維護者）：

```
【異常回報】<一句話標題>
環境：<OS / runtime / kit 版本 hash>
重現：<最小步驟或指令>
現象 vs 預期：<一行 vs 一行>
根因：<檔案:行號＋判斷邏輯，查不到就寫「未定位」>
影響：<下游影響鏈，最高風險情境>
建議：<修法方向＋設計約束提醒>
暫時繞法：<有就寫，沒有寫「無」>
```

## C. 建議模式（沒壞、但想優化——輕量建議單，不動手修）

適用：skill 能跑，但覺得流程多一步、觸發詞叫不到、輸出格式不合用、想加個選項／功能。**不要求重現步驟與根因**；一樣不改 kit 檔案——想先試改法就寫在建議單的「我試過的改法」，不要直接改 junction 內的檔。

只收四件事，使用者已講清的不再問：

1. **哪支 skill、哪一步**：skill 名＋流程中的哪個環節（例：imagen 的確認框那步）
2. **現況 vs 希望**：現在怎樣、希望變怎樣，各一行
3. **理由**：為什麼這樣比較好——發生過什麼情境、省什麼、避免什麼
4. **影響範圍**（盡力即可）：只有自己這樣用、還是組上多數人都會遇到；會不會跟 kit 既有規則衝突（查得到就附 SKILL.md 的段落）

「我試過的改法」是選填：使用者沒提就填「無」，不追問。

**輸出格式**（固定，交給使用者轉發維護者）：

```
【建議】<skill 名>：<一句話標題>
位置：<流程哪一步>
現況 vs 希望：<一行 vs 一行>
理由：<情境／省什麼／避免什麼>
影響範圍：<只有我／多數人；與既有規則有無衝突>
我試過的改法：<有就寫，沒有寫「無」>
```

## D. 使用回顧模式（批次回顧近期使用，一次產出整包報告）

給「用過 kit 一陣子」的人跑：把散在各對話裡的卡點一次撈出來，維護者據此改 skill。**同樣不改 kit 檔案**。省 token 的關鍵是**先用腳本掃、模型只讀摘要與被標記的片段**，不整份重讀對話紀錄。

1. **環境**：kit 版本 hash（同 A.1）；回顧期間預設近 30 天，使用者指定就照指定
2. **掃對話紀錄**（本機、只讀）：`python <skill-dir>/scripts/usage_scan.py --days 30`——列出每支 kit skill 的使用次數、被使用者糾正的訊息、工具錯誤片段。腳本把 skill 呼叫後 5 則使用者訊息視為「使用中」，**片段可能誤歸屬**，下一步要核
3. **核片段**：只挑被標記的片段，必要時打開該 session 的 jsonl（`~/.claude/projects/*/<id 前 8 碼>*.jsonl`）讀前後幾則確認來龍去脈；每筆判成四類之一：
   - **異常**：kit 腳本或規則錯了 → A 格式
   - **建議**：能跑但不順、要多次糾正才對 → C 格式
   - **已修**：查 `CHANGELOG.md` 對方版本之後已處理 → 只列一行「已於 vX.Y.Z 修，請升級」
   - **不回報**：個人偏好、與 kit 無關（權限擋、網路、使用者改主意）→ 只計數不出單
4. **企劃 lint**（有用 kit 寫過企劃才做）：用 AskUserQuestion 問一次「近期用 kit 寫或改過的企劃連結」（可多筆、可略過），逐份跑 `python <kit>/skills/plan-dept14-writer/scripts/plan_lint.py <網址> --no-lists`。**重點不是修這份企劃，是找「重跑 QA 還會出現」的共通問題**：同一類問題（標題跳號、引用失效、流程圖出口對不到規則…）在 2 份以上出現 → 出一張 C 單，「希望」欄寫要改哪支 skill 的哪條規則才能在寫的當下就避免
5. **輸出**一份報告（固定格式），先完整給使用者看：

```
【kit 使用回顧】<姓名或代號>／<期間>／kit <hash>
使用統計：<skill：次數／糾正／錯誤，一行一支，只列有用到的>
企劃 lint：<N 份；共通問題：類型 × 份數，沒有寫「無」>

<數張【異常回報】，格式同 A>
<數張【建議】，格式同 C>

已修（請升級）：<條列或「無」>
不回報：<類別 × 筆數，一行>
```

6. **隱私**：報告只引用必要的一兩句原話；企劃內容、同事姓名、連結照原樣給維護者沒關係（內部傳遞），但提醒使用者**別貼進公開頻道或 repo**；腳本已遮蔽金鑰特徵，輸出前再看一眼
7. **私訊給維護者**（使用者確認後才發）：
   a. 用 AskUserQuestion 問一次「報告內容可以直接私訊給 Tim 嗎？」——選項：直接傳／我要先改幾處／不傳我自己轉。要改就改完再問一次；不傳就到此結束，提醒他自己轉
   b. **鎖定收件者**：用 Slack 工具（claude.ai Slack 連接器的 `slack_search_users`，或秘書 kit 的 Slack MCP）搜「Tim大蔥」，**顯示名稱完全相符**才用；找不到或有多個相近名稱 → 列候選讓使用者單獨選這一題，不猜。repo 不寫死維護者的 Slack ID
   c. **發送**：私訊（DM）給該使用者。報告超過約 3,500 字就拆多則——第一則放【kit 使用回顧】標題行＋使用統計＋企劃 lint 摘要，其餘各張單依序回覆在同一串（thread），一張單不拆在兩則中間
   d. **讀回驗證**：發完讀回那段對話，確認每一則都在、沒被截斷；有缺漏就補發缺的那則，不整串重發。回報使用者「已私訊 Tim，共 N 則」
   e. **沒接 Slack**（沒有 Slack 工具或授權失敗）→ 不代裝，改成把報告整段給使用者，請他自己私訊 Tim

## B. 收單模式（維護者流程）

1. **逐項驗證回報**：對著原始碼核對每個聲稱（行號、邏輯、根因）——不輕信也不急著駁回；回報有誤就記下實際情況，回覆時溫和更正
2. **實測重現**：照回報步驟跑一次；**邊界也要實測**（例：回報建議「跟 API 要另一種格式」→ 真的打 API 確認支不支援，別憑印象答）
3. **設計修法**：遵守該模組的原設計約束（零依賴／單檔／向下相容）；回報者的建議可用就用並在回覆中歸功
   - **收回報者附的檔案進 kit 前，逐檔讀內容判斷能否公開**——kit 是公開 repo。未上線企劃內容（活動名、玩法、數值、畫面）、同事真名與帳號、內部原表／頁面連結不進 repo，移到網芳 `一四部企劃範本\kit-assets\<skill>\`，kit 內改去識別化範例。推之前除了金鑰特徵，也 grep 一次企劃名、人名（前科：v3.19.0 收 art-request-sheet 整包照搬，只掃金鑰就推上 main，事後改寫歷史）
4. **分層測試**：
   a. 單元層：偽造觸發條件（假回應、假輸入）驗證修正路徑與 exit code
   b. E2E 層：跑一次真實流程確認無迴歸
   c. 測不到的（需特定環境）明講「未測，理由」
5. **教訓回寫**：這個坑對使用者有行為指引價值的（例：遇到 X 錯誤該怎麼辦），寫回對應 SKILL.md 的 quirks／注意事項段——規則貼動作處
6. **CHANGELOG**：修正條目註明「組員回報」、採納的建議註明「組員建議」，讓回報者看得到自己的貢獻
7. **標準回覆**（給回報者）：哪些屬實照修、哪些查證後不同（附證據）、修在哪版、怎麼拿到（「starter 升級」）；回報品質好就明講好在哪，鼓勵下次照同規格

**建議單走簡化路徑**：跳過第 1–2 步（沒有要重現的東西），直接判三種結果——**採納**（改 SKILL.md、CHANGELOG 註明「組員建議」）／**部分採納**（說明取哪段、為何不全取）／**不採納**（附理由：與既有鐵則衝突、只對單一情境有利、成本高過收益）。不採納也要回覆，別讓建議石沉大海。

## 收尾自檢（事件觸發，不是每次都跑）

使用 kit skill 的任務收尾時，Claude 自問一次：本次有沒有發生以下任一事件？
1. 使用者糾正了 kit skill 的產出（不是單純改需求）
2. kit 腳本報錯、或需要繞路才完成
3. 發現 SKILL.md 寫的與實際行為不符

**有** → 在交付訊息最後附一張 A 或 C 單草稿，問一句「要轉給維護者嗎？」，使用者說要就交給他轉發；**沒有 → 什麼都不說**。不另外呼叫 skill、不重讀對話，成本只有收尾時的一次判斷。同一個問題一次對話只出一張單。

為什麼不做成「每次用完都跑一遍的回顧 skill」：每次都要載入整支 skill 指令並重看整段對話，多數時候什麼都沒找到，Token 與注意力都花在噪音上；踩雷當下用事件觸發抓、平常累積的用 D 模式定期批次掃，兩層就夠。

## 鐵則

- 回報模式與建議模式絕不修改 kit 檔案；收單模式修完必測才交
- 建議單不採納也要回覆理由
- 驗證結論要有證據（實測輸出、API 回應、行號），「應該是」不算驗證
- 回報與回覆一律繁體中文，code 引用保留原文
