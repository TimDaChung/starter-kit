# 拆列與設計描述寫法

## 拆列

依企劃〈3.呈現〉章的小節順序，一個畫面或一個狀態一列：

| 企劃內容 | 拆法 |
|---|---|
| 入口類（大廳泡泡框、活動入口、新聞牆 banner） | 各一列 |
| 主介面 | 依狀態拆：`主介面—活動進行中`、`主介面—活動結束後(A 玩家視角)`、`主介面—活動結束後(B 玩家視角)`、`主介面—<特殊結束狀態>` |
| 動畫（切換、主玩法演出、結算表演） | 各一列，動態填 O |
| dialog、提示橫條 | 各一列；用公版的也列，描述第一點寫「使用公版 XX」 |
| 同畫面只有小差異的狀態（已達／未達門檻） | 不拆列，用參考圖1／2 對照，描述裡寫「（參考圖1）」 |

命名用全形破折號「—」，視角放半形括號：`主介面—活動結束後(A 玩家視角)`。

說明頁預設不列（原表也沒有）；企劃說說明頁要美術出圖時才加一列，交付時提一句。

## 設計描述

格式：

```
1. 第一層用數字
    a. 第二層用小寫字母，縮排 4 個半形空白
        1. 第三層再用數字，縮排 8 個
```

只有一層子項、而且子項是並列清單（排名、頭貼、名稱…）時，第二層也可以用數字，跟原表一致即可。

內容規則：

1. **沿用企劃原文**，只改到能獨立閱讀：把「見核心計算規則」換成實際數值，把「同上」換成具體內容。
2. **從規則章補美術開工要的資訊**，原表沒有、但美術會回頭問的：
   - 盤面／格子配置（格數、相鄰限制、初始朝向、每格內容）
   - 花費數值、獎項數值
   - 交付檔名與 spine 動畫命名（企劃〈檔案歸檔路徑與命名規則〉）。寫在對應元件後面的括號裡，例：`2. 背景＋標題（1張圖，交付檔名：background.jpg）`
   - 演出期間的鎖定行為、跳過規則
3. **一張圖包含多個元件時寫明**：「背景＋標題（1張圖）」、「三個數值格子（1張圖）」。
4. **數字顯示規則**：千分位、最高位數、單位文案（「張」「人」）照寫。
5. **狀態條件**寫成「條件：結果」：`道具不足：顯示綠色按鈕，文案固定「前往」`。
6. 對應參考圖時在句尾加「（參考圖N）」。
7. 企劃待定的值照抄「後補」並標紅，不要自己填數字。

## 美術字（F 欄）

**預設留空**（2026-10-05 定案，實際兩份表這欄都是空的）。spec 不放 `art_text`，也不在缺漏清單問美術字。

只有使用者明講要填時才填：列畫面上要做成美術字的固定文字（標題、區塊標題），後台可設定、程式顯示的文字（活動名稱、倒數、數字）不列。

## 參考圖分配

| 情況 | 放法 |
|---|---|
| 一張示意圖 | G |
| 同畫面不同狀態（已達／未達、置頂／置底／原位） | G、H、I 依描述裡的「參考圖N」順序 |
| 影片 | 轉 GIF 放 G |
| 「圖後補」佔位圖 | 不放，描述寫「示意圖後補」 |
| 分類列、按鈕列這類局部截圖 | 放在主圖旁（例：活動入口 G＝入口卡片、H＝分類列） |

## 範例列（新系統，去識別化）

實際案例（含原表與企劃原文）屬機密，放在網芳 `X:\grp.product.pm1\2. 產品改造\一四部企劃範本\kit-assets\art-request-sheet\實際範例.md`（X 讀不到換 Y:）；讀得到就先讀它校準寫法，讀不到照下面的通用範例。

**活動入口**｜動態 O｜G＝入口卡片、H＝分類列

```
1. 分類：熱門
2. icon（交付檔名：icon.png）
3. 活動名稱：抓取後台設定活動名稱
4. 簡單描述：<企劃寫的一句話賣點>
5. 按鈕
    a. 道具不足：顯示綠色按鈕，文案固定「前往」
    b. 道具足夠：顯示黃色按鈕＋刷光效果，文案：{[開始]}
6. 時間倒數抓取後台活動結束時間
    a. 剩餘時間≥24H，字體白色
    b. 剩餘時間<24H，字體黃色
```

（`{…}` 是 spec 裡的紅字標記）

```
    b. 等級 2：待機 idle02、中獎 ani_win02
```

## 改版企劃（只寫變動）

**怎麼判斷**：企劃有調整標記（灰底刪除線＝廢除、綠底＝本次生效），或〈目的〉寫「本次調整方向」「既有系統改版」。新系統企劃照上面的完整寫法；改版企劃改用這節。

美術拿到改版需求只需要知道「這次要動哪裡」，整個畫面重列一遍反而要他自己比對新舊。所以：

1. **只列有變動的畫面**，沒變動的畫面不列。
2. **只是沿用現有素材的狀態不另開列**（現有 dialog、既有的反灰按鈕）；有新畫法才開。不確定算不算新畫法，就併進主畫面那列寫一句，交付時提出來問。
3. **設計描述分上下兩段**：
   - 上段：只寫變動，一條一件事，寫成「哪個元件＋怎麼變」，不寫沒變的元件、不寫廢除的舊值
   - 一行 `===================================` 分隔
   - 下段：美術畫圖需要的完整資料清單，**照畫面上實際顯示的完整字串**列（既有＋新增都列，例：`<底台> <遊戲名>(新章)`），讓美術不用回企劃查
   - 只有一兩條變動、沒有資料清單時，可以只有上段
4. **新增元件可以附美術方向建議**，寫成「建議…」（例：「標籤選色建議用紫紅色」），依據是畫面既有配色，不要編造理由。
5. **紅字只標企劃標了「待確認」的值**；改版描述整段都是變動，不必再標紅。

範例（去識別化，3 列；實際案例見網芳 `實際範例.md`）：

**活動列表**｜X

```
1.某場次按鈕文案調整，文案：每週五 00:00～24:00
```

**活動主介面**｜X

```
2.開始按鈕左右增加箭頭，按鈕裡增加目前選擇中的場次文案

    a.場次 1（照畫面完整字串）
    b.場次 2（新增）
2.遊戲 B

```

```
    1.同時擁有兩個標籤則顯示：既有標籤>活動
2.標籤選色建議用紫紅色
```

## 常見缺漏（交付時檢查這幾類）

- 企劃示意圖上的數字和規則章不一致（例：圖上 600、規則寫 500）
- 兩種叫法沒寫對應（小／中／大 vs 等級 1／2／3）
- 公版效果算不算動態（刷光、彈出動畫）
- 圖後補、秒數後補
- 說明頁要不要美術出圖
