# 企劃一部寫企劃（plan-dept1-writer）

產出或修改符合團隊規範的企劃，含流程圖。適用所有企劃類型：模組化活動、系統功能、版本需求、行銷活動。

流程圖規範已內嵌於第八節；初稿或修正完成後呼叫 `plan-doc-qa` 複查，審查報告連同交付，有紅燈先修再交。

## 一、模式判斷（動工前先做）

先判定這次是「全新」還是「調整」，兩者流程不同。判斷依據依序：

1. 使用者提供了現有企劃來源（Notion 連結、PDF、貼上全文）：→ **調整模式**
2. 用詞帶「改、調整、補、新增、抽換、修、重寫某章、上次那份」：→ **調整模式**
3. 同一對話中本 skill 已產出過一版，使用者接著提出修改：→ **調整模式**
4. 只有點子、需求、參數，沒有現有文件：→ **新建模式**
5. 兩種都像（例：「參考舊活動寫一份新的」）：→ **新建模式**，舊文件只當參考，且開工前先跟使用者確認一句。

**例外**：使用者給的 Notion 連結是「空白部門模板」時，仍屬 **新建模式**，該頁只當最後回寫的目標頁。

判定結果要在回覆開頭用一句話說明。

## 二、新建模式流程

1. **確認必填參數**（缺什麼用 AskUserQuestion 一次問完，不逐題來回）：
   a. 企劃類型、**官方模組名稱**與包裝主題
      i. 官方模組名稱是標題第一段，不是包裝名。例：「允許 PM 未來換皮、工程先做架構調整」這類改版官方叫**回收活動模組**。不確定就問，不自行命名。
   b. 程式代號、PM、負責範圍標記（A/C/S，**半形斜線**）
   c. **目的章影響範圍五項（必填，一項不能缺）**：影響遊戲、正式區生效日、限制版本號、影響玩家群體、影響平台
      i. 使用者沒提供就**必須主動問**，不可留空、不可自行推測、也不可全寫「後補」就過。
   d. 目的（3～5 點方向）、走期規則
   e. 核心數值與獎勵 id／包裹 id
   f. **會用到的公版及其編號**（獲獎 dialog、橫條提示、排行榜…）——不知道有哪些公版可選就**直接問**，不可只寫「公版」帶過（那種公版只有單一版型的情況見六、3.2（3）第 6 條）
   g. 是否需要說明頁、埋點、後台設定
2. **判斷章節取捨**：骨架八章固定不變，用不到的章節保留標題並寫「本次不適用」。
3. **先跑介面逐畫面確認**（見第七節），畫面全部確認完才組裝全文。
4. **產出全文**（依第六節各章規則）。
5. **畫流程圖**（依第八節）。
6. **複查**：呼叫 `plan-doc-qa`。

## 三、調整模式流程

1. **先讀完現有全文**，不憑記憶或推測。
2. **先複述再動手**：用一到三句複述要改什麼、動到哪些章節。意圖不明確就問。
3. **只改指到的區塊**：未被點名的章節、段落、措辭一字不動。
4. **使用者可能已經手動改過頁面**：每次調整前重新讀一次現有全文，以頁面的實際內容為準，不以本對話先前的版本為準；發現使用者手改的地方不要改回去。
5. **使用者手改的內容先看懂再動**：他手改的寫法往往比原本精確（書面門檻取代抽象標準、多一層降級狀態、數值直接寫進條文），先弄懂他為什麼這樣寫，不要用自己的寫法覆回去。
6. **連動檢查**（必做）：改完之後主動比對下列連動關係，找到不一致就列出來問使用者，不自行改：
   a. 改規則（第 4 章）→ 檢介面元件清單、說明頁、流程圖、後台設定
   b. 改數值／獎勵表 → 檢說明頁獎勵一覽、獎勵 id、包裹 id、千分位顯示
   c. 改介面元件或畫面名 → 檢規則章與說明頁是否還用舊名稱、可更換包裝檔名、banner type
   d. 改走期／結算 → 檢流程圖結算節點、保留入口規則、寄信時間、說明頁注意事項
   e. 改平台／版本限制 → 檢目的章影響範圍表、規則章平台限制、設定章最低支援版本、說明頁注意事項第一條（四處要一致）
   f. 改名詞叫法 → 全文搜替，含表格、流程圖標籤、信件文案
   g. 改一種「狀態」的呈現 → 檢其他狀態是否被混在同一條裡
   h. **新增一條可以讓玩家回到前一步的捷徑**（例：dialog 直接再轉一次）→ 檢流程圖有沒有這條路徑、規則章有沒有寫、提示與錯誤處理是否沿用
   i. **新增或刪除 H3 小節（含介面章的畫面）** → 重數一次分隔線，確認仍符合「只有 H3↔H3 加」
   j. **改「組數、數量」（例：轉盤兩組 → 三組、獎勵分層數變更）** → 這類改動會散在**五處**：介面章元件清單、規則章、說明頁、後台章設定項、流程圖節點文字；一處一處核。另外回頭看**後台章的「工程預設值」是否還成立**——規則從「一個門檻值」改成「一段判定邏輯」時，預設值那行要一併改寫
7. **輸出格式**：默認只給**變更的章節片段**＋一張變更對照表。
8. **補調整紀錄**：格式一律為「日期　姓名　調整內容」。
9. **複查**：呼叫 `plan-doc-qa`。
10. 若要直接回寫 Notion 頁面，先明講要動哪些區塊並取得同意。
11. **修錯字時先確認字碼**：形近字（券／劵、次／吃、反／返）很容易在 old_str 裡打錯字碼導致替換無效；改完要回頭檢查回傳內容是否真的換掉。

## 四、調整標記規範（調整模式專用，硬性規定）

舊內容一律保留不直接刪除，讓工程、美術、QA 看得出改了什麼。

### 4.1 修改既有內容

1. 原項目保留，整個 block 套**灰底**，文字加**刪除線**。
2. 在原項目下方新增一個**降一層**的子項目，套**綠底**，寫新內容。
3. 層級依循環規則往下降：`1.` → `a.` → `i.` → `1.` …
4. 範例：

```
4. 拉斯維加斯
   a. 〖灰底〗~~文案：每週五 21:00～23:00~~
      i. 〖綠底〗文案：每週五 00:00～24:00
```

### 4.2 既有項目新增內容

1. 原文完全不動，直接新增項目，套**綠底**，與同組其他項目**同層**。

### 4.3 刪除內容

1. 原項目套**灰底**＋**刪除線**，不新增綠底項目。

### 4.4 輸出方式

1. **直接回寫 Notion**：用 API 設 block 底色 `gray_background`／`green_background`，刪除線用 strikethrough annotation。
2. **交片段由 PM 手貼**：原文寫 `~~原文~~` 並在行首標 `〖灰底〗`，新內容行首標 `〖綠底〗`。
3. **表格內的調整**：改用儲存格內 `~~舊值~~ → 新值`，並在表格下方加綠底註記。
4. **流程圖的調整**：不在圖內標色，直接換新版，圖下以綠底一行註明改了哪些節點。

### 4.5 標記清除

1. 舊標記**不主動清除**；使用者要求時才清。

## 五、文件骨架（固定，順序不可調）

```
📌項目：[官方模組名稱]-[包裝主題]-[程式代號]／PM：[姓名]（A/C/S）

1.目的        → 影響範圍表＋目的條列
2.流程圖      → 玩家流程
3.呈現        → 美術需求表、介面（各畫面）
4.規則        → 數值、機率表都寫在條文旁邊
5.說明頁
6.設定        → 包裹、埋點/統計、其他（只放條文放不進去的）
7.後台        → 後台流程、查詢後台、調整後台
8.調整紀錄
```

標題行規則：第一段是**官方模組名稱**，第二段才是本檔包裝主題；負責範圍標記用**半形斜線**（A/C/S）；分隔用半形連字號。

### 編號層級（硬性規定）

1. 循環使用：`1.` → `a.` → `i.` → `1.` …，不設上限；內容上優先控制在三層內。
2. **已知限制（不要再試）**：Notion API 寫入的 `numbered_list_item` 一律帶 `list_format: numbers`，該欄位**唯讀**——create 與 update 帶上都會被 validation 擋下。API 寫進去的巢狀編號在 Notion 上會顯示成 1. → 1. → 1.，Claude 無法修正。
3. 需要 1. → a. → i. 時，請 PM 在 Notion 選取該層清單 → 右鍵／⸮ 選單 → 編號樣式。交付時主動告知這一句。
4. PM 手動調過樣式之後的修改，**優先用 `update_content` 局部替換**；整頁 `replace_content` 會重建所有 block，手調的樣式會被洗掉。

### Notion 標題層級（硬性規定）

1. 只有「項目」那一行用 **H1**，且只有它帶 📌。
2. 章節一律 **H2**，**帶章節編號、不加 emoji**。
3. 小節與介面章的每一個畫面用 **H3**，**不帶編號**，標題只寫畫面名本身。
4. Notion 只有 H1～H3，第四層改用**粗體段落**。
5. **分隔線規則（硬性）：全文只有 H3 與 H3 之間放分隔線 `---`**，其他位置一律不放：
   a. **H3 ↔ H3（同一章內相鄰的兩個小節、介面章相鄰的兩個畫面）→ 加**。
   b. **H3 ↔ H2（上一章最後一個小節接下一章標題）→ 不加**，讓 H2 本身就是最大的斷點。
   c. **H1 ↔ H2（📌項目行接 1.目的）→ 不加**，文件最上方沒有分隔線。
   d. 因此每一章的**最後一個 H3 下方不補分隔線**，下一章 H2 直接接上。
   e. 增刪 H3 時要順手重數一次，避免出現「連續兩條分隔線」或「章尾多一條」。
6. 用 API 做 find-and-replace 改標題時，`## 後台` 會跟 `### 後台流程` 撞到；old_str 帶下一行一起比對就不會撞。
7. 批次調分隔線時，`update_content` 的 old_str 要把 `---` 與相鄰的標題綁在一起比對（例：`---\n## 2.流程圖`、`### 介面\n---\n### 大廳地列入口`）；單獨用 `---` 當 old_str 會比對到多處而失敗。
8. **大幅度結構搬移才用整頁 `replace_content`**；十項以內的小修一律用 `update_content`。
9. 參數形狀：`update_content` 帶 `{"content_updates": [{old_str, new_str}]}`；`replace_content` 帶 `{"new_str": "…全文…"}`。
10. 文字上色用 `<span color="red">…</span>`／`<span color="blue">…</span>`，在段落、清單、表格儲存格、H3 標題內都有效；**但 mermaid 程式碼區塊內的文字無法上色**。

## 六、各章寫法規則

### 1. 目的

1. **章節開頭先放一張影響範圍表（項目／內容），五列必填**：影響遊戲、正式區生效日、限制版本號、影響玩家群體、影響平台。
2. **五列只要有一列使用者沒講，就要用 AskUserQuestion 問**。
3. 表下方再寫 3～5 點目的，動詞開頭，一點一句，同時涵蓋玩家體驗、營運效率、商業指標三種價值。
4. 表裡的版本號與平台要與第 4 章、第 6 章、說明頁注意事項完全一致。

### 2. 流程圖

1. 本章**只放玩家流程**，後台流程圖放第 7 章。
2. 圖需走完完整迴圈：觸發 → 判斷 → 執行 → 結果 → 下一輪 → 結算。
3. 結算相關節點要標明時間。
4. **每一種結局都要有自己的路徑**：成功、未達標、個人未中獎是三種不同結局。
5. **玩家可以跳回前一步的捷徑也要畫**（例：領獎 dialog 直接再轉一次），用虛線回頭線表示，不可只寫在介面章。

### 3. 呈現

本章依序放兩個部分：美術需求表（H3）→ 各畫面（每個畫面一個 H3）。

#### 3.1 美術需求表

1. **本 skill 不產出任何美術需求內容**。本小節只留標題與一行「1. 正式需求表：」給 PM 自行貼連結。

#### 3.2 介面（寫法核心，硬性規定）

**介面章是寫給 client 看的元件清單，不是規格書。**

**（1）畫面怎麼拆**

1. **依「client 要分別實作的位置」拆，不依功能概念拆**。同一個「入口」分散在三個位置，就是三個畫面。
2. **畫面名用團隊既有的位置術語**（大廳地列入口、活動入口、新聞牆），不自己造描述性名稱。不確定叫法就問。
3. 每個畫面一個 H3，依玩家動線排序。

**（2）畫面排版**

1. 每一個畫面都是「H3 標題 → 兩欄」，畫面之間用**分隔線**隔開（即五、Notion 標題層級第 5 條的 H3↔H3 規則）；**本章最後一個畫面下方不補分隔線**，因為接著就是下一章 H2。
2. 左欄：元件清單；右欄：畫面圖。
3. Notion 兩欄寫法：`<columns><column>…</column><column>…</column></columns>`；分隔線用 `---`；高度差太多用 `<empty-block/>` 補齊。

**（3）元件清單怎麼寫**

1. **順序照畫面上實際的擺放位置**（由外框到內容、由上到下），**不是照資訊重要性或邏輯分組**。
2. **同一區塊的元件要黏在一起**（例：右上角的紅利餘額與說明頁相鄰）。
3. 把該畫面所有元件列出來，**連背景、標題、返回鍵這種純美術元件也要列**，且**只寫名字，一個字都不多**。
4. **右欄已經有圖時，位置資訊不要再用文字寫一次**（例：「說明，位置右上角，點擊開啟說明頁」→ 只寫「說明頁」）。
5. 判準：**這件事圖上看不出來、且 client 會做錯，才寫**。只有以下四種情況才補子項：
   a. 要抓後台／網芳／zip 才寫資料來源，且**要寫明抓哪一個欄位**（例：「時間倒數抓取後台活動**結束時間**」，不可只寫「抓取後台活動」）
   b. 同一元件有多種長相才寫狀態（見下一段）
   c. 會做錯才寫格式（千分位、`[MM/DD HH:MM] ~ [MM/DD HH:MM]`、單位字如「人」「張」）
   d. 會導轉才寫點擊行為，並附 banner type
6. **引用公版先問有哪些版型**，不可只寫「使用公版」帶過：
   a. 有多個版型可選 → **一定要帶編號**（例：「使用獲獎 dialog 公版 B01」）。
   b. **該公版只有單一版型（例：公版橫條提示）→ 不寫編號，也不寫「後補」**，直接寫「使用公版橫條提示」即可。
   c. 有編號但還沒定 → 寫「公版編號：後補」並標紅字。

**（4）按鈕與多狀態元件怎麼寫**

1. **狀態的判定條件要用「算得出來的門檻」，不用抽象標準**。
   a. 錯：「玩家達到領獎標準顯示【領獎】」——QA 無法寫成測試案例。
   b. 對：「紅利不足轉最小轉盤 10 次 → 綠色按鈕，文案固定：前往」。
   c. 自己想不出具體門檻就問使用者，不要自編一個抽象詞填上。
2. **按鈕文案是組合式的，變動部分用 `[]` 包起來**（見九、符號約定）。例：【轉 10 次[紅利icon]+[本轉盤轉十次紅利數量]】——固定文字、icon、動態數值三段要各自標出來，不可只寫【轉 10 次】。
3. **狀態要寫滿，不只有「可點」與「反灰」兩種**。常見的第三種是**降級**：
   a. 紅利夠 → 顯示【轉 10 次】
   b. 紅利不夠轉 10 次 → **降級顯示當下可轉最高次數 X**
   c. 可轉次數 < 2 → 才反灰
   寫按鈕時主動問使用者「不夠的時候是直接反灰，還是降級顯示？」。
4. 按鈕除了文案，**顏色與特效也是狀態差異**（例：綠色按鈕 vs 黃色按鈕＋刷光效果），client 決定不了，要寫。

**（5）右欄的圖**

1. **圖直接貼進右欄**，不做序號命名、不做圖檔對照表（圖由 PM 自己跟美術與多方部門確認）。
2. 一個畫面放多張圖時，**每張圖上方標《左欄的那個詞》**（例：《分類》《排行榜》《流標》）。
3. 尚未提供的圖，右欄寫「圖後補」。

**（6）點色規則**

1. **藍字＝右欄有對應圖的詞**，是圖文對照的錨點。沒有對應圖就不要標藍字。
2. **紅字＝本次要讓各方特別看到的重點資訊**。判斷標準是「這一行漏看會出事」，沒有固定情況，常見的有：
   a. 工程必須看到的實作重點（例：不做紅點）
   b. QA 必須驗證的項目
   c. PM 本次要複核的數值（花費、比例、起始值）
   d. 尚未確認的待填值「後補」
3. **已經填入的數值也可以標紅**，紅字不等於「還沒定」；填完也不用退回黑字。
4. **不設數量上限**（沒有「一個畫面最多一個」這種限制），但也不能全文都紅；不確定該不該標就問使用者「這一項要不要標紅」。

**（7）不可以寫的東西**

1. **不套五要素制式格式**（資料來源／狀態切換條件／顯示格式／視覺門檻／點擊行為）。
2. **不寫「是否變色？後補」這類替 client 想好的待辦問句**。
3. **不寫觸發條件與行為機制**——全部寫在第 4 章規則。

**（8）其他**

1. **能引用就引用**：行為與現有元件相同時寫一句帶過。
2. **所有 dialog 與公版提示都當成一個畫面寫在本章**，不另開「提示dialog」章節。
3. 長度自我檢查：入口、提示橫條這類畫面 1～5 行；主介面約 10～15 條；超過 20 行就是寫成規格書了。

### 4. 規則

1. 拆成多個**最小可測試**的小節，每節只講一件事。
2. **凡是「什麼條件會發生什麼」的內容一律進本章**。
3. 每條規則寫成「條件 → 行為」，並補齊例外、邊界、時間數字。
4. **數值直接寫在條文旁邊，不另做試算表**（見第 6 章）：花費、機率、比例、起始值、上限都跟著它所屬的規則走。
5. **機率表的寫法**：
   a. 條文先用佔位符寫一行（例：「依該轉盤獎項表獲得 \[數量1\]／\[數量2\]／\[數量3\] 張樂透券；分配如下」）。
   b. 下面**每一組一張表**，表前先標明該組的識別與單次花費（例：「轉盤2，轉單次花費 5,000 紅利」）。
   c. 表固定兩欄：獎勵／獲得機率；各組的機率結構保持一致，只差在數量倍率。
   d. 多組時編號要順（轉盤1／2／3），不可全部寫成同一個名字。
6. **不同狀態不可混在同一條**。例：「本檔流標（全體未達門檻）」與「個人未中獎（有開獎但沒抽到）」是兩件事。
7. **「活動結束」與「活動入口關閉」是兩個不同時點，要各自定義**：
   a. 活動結束＝玩家無法再遊玩（玩法停止，但入口還在，還能看排行榜）
   b. 活動入口關閉＝玩家不再能進入活動頁，也看不到排行榜
   寫「活動結束、資料保留與重置」小節時，這兩行放最前面當定義，後面的條款才有依據。
8. 能表格化就表格化，表格帶工程可直接取用的鍵值。
9. 未定值一律寫「後補」，不留空白、不寫假資料。
10. 工程預設但 PM 可調的值，規則裡要同時寫出「預設值」與「後台可調」，並與第 7 章一致。

### 5. 說明頁

1. 完全切換成**玩家視角**重寫，語氣官方但白話。
2. **本章一律要寫**；回寫 Notion 時自行新增 H2「5.說明頁」，位置在規則之後、設定之前。
3. **內部術語要翻成玩家語言（這是「同一名詞全文統一」的唯一例外）**：

| 內部（規則章、設定章） | 玩家（說明頁） |
|---|---|
| 全神幣遊戲 | 列出實際遊戲名（例：16張麻將、13張麻將、大老二、接龍、13支、鋤大D） |
| MB 平台 | 手機版、PC登入新版 |
| v20.3 以上 | v20.3（含）以上 |

   不確定某個內部詞對玩家要怎麼講（例：涵蓋哪幾款遊戲）就問，不自行列舉。
4. 固定結構，順序不可調：怎麼玩 → 計算規則 → 獎勵與領取 → 獎勵一覽 → 排行榜（如有）→ 注意事項。
5. 內部資訊一律不出現：award_id、包裹 id、網芳路徑、wid、banner type、公版編號、後台欄位名；機率除非確認要公示，否則不寫。
6. **機制若有「玩家容易誤解」的落差，必須在計算規則用一句話定調，並在注意事項再寫一條**。
7. 注意事項固定收尾，依企劃調整措辭但不可少：
   a. 支援平台與最低版本（用玩家語言，且與目的章的內部寫法對得起來）
   b. 獎勵內容以遊戲內實際顯示為準
   c. 獎勵寄送方式與領取期限，逾期失效
   d. 同分／同名次或隨機抽選的判定方式
   e. 活動結束後未領取視同放棄，恕不補發
   f. 系統異常、外掛或不正常遊玩行為，官方有權修正或取消資格
   g. 個人裝置或網路因素導致無法參與，官方不負責
   h. 官方保留最終裁定權與調整、中止活動之權利

### 6. 設定

**本章只放「規則章條文放不進去」的東西**，不重複收一份數值。固定三個 H3 小節：

1. **包裹**：獎勵包裹 id、信件 ID、信件文案（文案已寫在規則章就指向規則章，不再貼一次）。
2. **埋點/統計**：**不產出指標表**（每次由 PM 自己寫），固定只放一行 BQ 埋點表連結：
   `https://docs.google.com/spreadsheets/d/1vSoba58s7BOjLPxx-WdALtTy7JKNr_wHP7TXS_FiPPg/edit?pli=1&gid=917650002#gid=917650002`
3. **其他**：零散項與待補項（最低支援版本、banner type、刷新頻率、演出秒數…）。介面章已經填好的值要同步這裡，不可一邊已填一邊還寫後補。

**不再寫「試算」與「上傳」兩個小節**：數值跟著規則條文走；美術上傳路徑與可更換包裝命名寫在規則章的「檔案歸檔路徑與命名規則」小節。

### 7. 後台

1. **本章第一個 H3 是「後台流程」**。
2. **查詢後台**（H3）：規則＋網址。
3. **調整後台**（H3）：規則＋網址，設定需求分成：
   a. 通用設定：活動名稱、類型、狀態、起訖時間、排序權重
   b. **本模組專屬設定：PM 每次手動填的欄位，實務上通常只有「數值」**（花費、機率、比例、上限）；包裝素材、包裹 id、文案 id 這些可能走別的流程或屬工程預設，不確定就問，不要全塞進 PM 設定
   c. 工程預設值（預設收合），且與第 4 章規則寫的預設值一致。**規則從單一門檻值改成一段判定邏輯時，這裡要一併改寫成那段邏輯**，不可還寫成「…之門檻」
   d. 維運工具：數值調整／重置、手動結算按鈕、假資料按鈕（僅測試區）
4. 註明資料保留期。

### 8. 調整紀錄

1. 文末固定保留區塊，第一行寫格式說明：「完成調整後請新增一筆，格式：日期　姓名　調整內容」。
2. **每一筆紀錄都要帶操作者姓名**，且內容要寫明**是用 AI 調整了什麼**。
3. 使用者自己手改的部分也要另起一筆（例：「手動改寫介面章：…」），與 AI 調整的分開記。
4. 同一輪內的多項 AI 修改**合併寫成一筆**，不一項一筆。
5. 新建時同時寫入第一筆建立初版紀錄。

## 七、介面逐畫面確認流程（第 3 章專用）

### 7.1 步驟

1. **先列畫面清單**：從第 2 章流程圖推導，並**依「實作位置」而非功能概念拆**，給使用者確認增刪、順序與**畫面名稱叫法**後才開工。
2. **逐畫面跑**，每一輪只處理一個畫面：
   a. 先列出該畫面預期會有的**元件清單**（含背景、標題等純美術），請使用者增刪
   b. 用 AskUserQuestion 一次問完該畫面 3～4 個**會影響 client 實作的決策點**；有按鈕就要問到**具體門檻與所有狀態（含降級）**，有公版就要問到**有哪些版型、需不需要寫編號**
   c. 使用者沒指定的細節不自行補問句，直接不寫；真的是待填值才寫「後補」
   d. 該畫面確認完才進下一個，已確認的畫面不重寫
   e. 使用者的回答若與先前已確認的設定矛盾，要直接指出並請使用者裁示
3. **每輪結尾回報進度**：已確認 X／Y 個畫面，下一個是哪一個。
4. **全部確認完才組裝介面章**；過程中收集到的觸發條件與行為機制同步整理成第 4 章規則小節。

### 7.2 圖的處理

1. **圖由 PM 自己管**：不做序號命名、不做圖檔對照表。
2. 使用者貼圖後，圖直接放該畫面的右欄；一個畫面多張圖時，每張圖上方標《左欄的那個詞》。
3. 未提供圖的畫面，右欄寫「圖後補」。
4. 貼圖後順便做**反向校對**：圖上有但清單未列的元件、清單有但圖上沒有的、狀態未定義、格式不符。只列問題，不自行改寫。
5. 圖上看得到的位置資訊，左欄就不要再寫一次。

### 7.3 例外

1. 使用者明說「你先草一版」時，才一次寫完並全部圖位標「圖後補」。
2. 調整模式只跑被指名的畫面。

## 八、流程圖規範（固定，不得自行發揮）

### 8.1 流程類型與擺放位置

1. **玩家流程**放第 2 章；**後台流程**放第 7 章第一個 H3。
2. 未定數值一律標「後補」，**絕不捏造**。
3. 若圖與規則區互相矛盾，先向使用者指出並確認。
4. **圖只畫動作與判斷，不把介面上看得到的資訊寫進節點文字**。
5. 規則有門檻值時，節點寫「是否大於 XX 門檻？後台可調，預設 N」。
6. 每一種結局都要有結尾節點；成功、未達標、個人未中獎要各走各的。

### 8.2 Mermaid 語法規範

1. 一律 `flowchart TD`，標籤全繁體中文，多行標籤用 `<br/>`。
2. 節點形狀：`[方框]` = 頁面／狀態、`(圓角)` = 動作、`{"菱形"}` = 是／否判斷。圓角節點用半形括號。
3. 邊標籤 = 使用者動作：`點擊`、`進入活動`、`是`／`否`。
4. 顏色一律同時指定 fill、stroke、stroke-width 與 **color**，並加上 init 區塊：

```
%%{init: {'theme':'base','themeVariables':{'fontSize':'14px','textColor':'#1a1a1a','lineColor':'#5c6570','edgeLabelBackground':'#ffffff','mainBkg':'#ffffff'}}}%%

classDef startEnd fill:#ffd6e0,stroke:#c2255c,stroke-width:2px,color:#1a1a1a
classDef decision fill:#ffe8a3,stroke:#c77700,stroke-width:2px,color:#1a1a1a
classDef action   fill:#c5e4ff,stroke:#1864ab,stroke-width:2px,color:#1a1a1a
classDef dialog   fill:#ded0ff,stroke:#5f3dc4,stroke-width:2px,color:#1a1a1a
classDef reward   fill:#c6f6cd,stroke:#2b8a3e,stroke-width:2px,color:#1a1a1a
classDef page     fill:#f1f3f5,stroke:#495057,stroke-width:2px,color:#1a1a1a
```

起訖點粉／判斷橙黃／動作藍／Dialog 紫／獎勵綠／頁面灰。

5. 回頭迴圈用虛線 `-.->`，並以 `linkStyle` 設灰色。**linkStyle 的索引是邊的宣告順序、從 0 起算，每次改圖必須重數一次**。注意 `-.->` 在 grep 時容易漏抓，比對式要用 `-\.?->`。
6. **起始節點必須置頂**：不得有任何 incoming edge。
7. **禁用巢狀 subgraph**。

### 8.3 排版：讓圖一路往下讀（重要）

mermaid 是自動排版，沒有鎖位置的設定，只能用**宣告順序**引導它：

1. **主線先宣告、例外分支後宣告**。dagre 是「誰先寫、誰排左邊」，把例外寫在前面會把主線擠成之字形。每個判斷都把**主線那條寫在前**，並把整條主線一次寫完、例外分支統統放到最後面。
2. **回頭迴圈不要接到起始節點的下一格**；改接到再下一格，最上面三格就會垂直對齊。
3. **同一分支內優先串接，不平行分岔**（例：中獎分支寫成排行榜 → 寄信 → 領獎）。
4. 共用終點要小心：兩條長短差很多的分支接到同一終點時，短的那條會被拉出很長的線；寧可讓短分支自成終點。
5. **重排宣告順序不算簡化流程**，但節點文字與分支邊標籤一字不改。

### 8.4 流程圖交付規範

1. **先渲染再交付，而且自己要看過圖**。渲染方式依環境：
   a. **Windows 本機（Claude Code，組員預設環境）**：`npx -y @mermaid-js/mermaid-cli -i flow.mmd -o flow.png`（需 Node；首次執行會下載瀏覽器，較慢）。已裝 Playwright 的機器可免二次下載：建 `pptr.json` 填 `{"executablePath": "<%LOCALAPPDATA%\ms-playwright\chromium-*\chrome-win*\chrome.exe 的實際路徑；新版 Playwright 是 chrome-win64>"}`（目錄帶版本號，先用 dir 找再填，不可寫死），加 `-p pptr.json`。
   b. **claude.ai 容器**：用 mmdc，Chrome 路徑用 `find /opt/pw-browsers -name chrome -type f` 找（目錄帶版本號，不可寫死），以 `-p pptr.json` 帶 `{"executablePath":"…","args":["--no-sandbox","--disable-dev-shm-usage"]}`。
   c. **兩者都不可用**（無 Node 或下載失敗兩次）：不硬渲染——把 mermaid 原始碼貼進 Notion `/code` 區塊（語言選 Mermaid）由頁面渲染，並請使用者回饋圖有沒有排歪；交付訊息註明「本次未做本地渲染自檢」。
2. 渲染後自己讀一次 PNG，確認：主線是不是一路往下、起始節點有沒有被擠到旁邊、每個節點的出口線清不清楚、虛線有沒有接錯、標籤有沒有重疊。不滿意就重排再渲染。
3. 使用者說「線沒接到」時，**先回頭核對原始碼**——很常是線有接、只是排版讓它看起來斷了；先說明事實再修排版。
4. 對話中附 Notion 貼法：「輸入 `/code` 建立程式碼區塊，語言選 Mermaid」。
5. 提醒：mermaid 程式碼區塊內的文字無法上色，所以圖裡的「後補」不會跟全文一樣變紅字。

### 8.5 流程圖修改禮儀

1. 只執行使用者明確指到的修改。
2. **絕不主動合併節點或簡化流程**——曾被 revert 過。為了排版而重排宣告順序是例外，但節點內容不變。
3. 按鈕文案、分支結果文字逐字照改。
4. 每次改完重新渲染 PNG 交付。

## 九、通用寫作規則

### 9.1 符號約定

1. **`[]`＝裡面的內容全部由工程判斷可顯示的內容，可依條件變動**。這是團隊的固定約定，不是隨手加的括號：
   a. 【轉 10 次[紅利icon]+[本轉盤轉十次紅利數量]】——icon 與數值由工程帶
   b. 文案：[抽獎]——整段文案依條件變動
   c. `[MM/DD HH:MM] ~ [MM/DD HH:MM]`——時間由後台帶
   固定不變的文字就不要包 `[]`；包了 `[]` 就代表告訴 client「這裡不是寫死的」。
2. **`{}`＝系統端的實際變數名**，與 `[]` 是兩套符號，不可混用：
   a. 信件文案用 `{}`，照工程實際的變數名填（例：`恭喜您於{moduleName}中獎！`、`{award}`）。
   b. `[]` 是寫給 client 看的「這段可變」；`{}` 是真的要貼進系統的字串，不確定變數名就問，不自編。
3. 【】用來包整顆按鈕；《》用來標右欄圖的名稱。

### 9.2 用詞與待填值

1. 同一名詞全文統一；畫面名一旦定案，規則章、說明頁、埋點表都要用同一個名字。**唯一例外是說明頁**（見六、第 5 章）。
2. **獎金池、獎勵、排行榜的共用範圍內部一律講「全神幣」或「全神幣遊戲」，不使用「全服」**。
3. **待填值一律只寫「後補」兩個字**，不加〔〕、不寫「連結後補」這種前綴。
4. **全文的「後補」都標紅字**（`<span color="red">後補</span>`）；交付時另外把所有後補依負責方分組列出（數值／PM、美術、工程、文件）。mermaid 區塊內的後補無法上色，要主動說明。
5. **名詞定案前先檢查是否會誤導玩家對機制的理解**（例：「抽獎券」會讓玩家以為券多比較容易中獎）。
6. 數字一律千分位；時間一律 `MM/DD HH:MM`。

### 9.3 其他

1. **顏色的兩種用途**：
   a. 紅字 —— **本次要讓各方特別看到的重點**（工程要看、QA 要驗、PM 要複核的數值、待填值「後補」），沒有固定情況、也沒有數量上限，已填入的數值一樣可以標。

3. 每條規則都要能被 QA 直接寫成測試案例；寫不出測試案例代表門檻不夠具體。
4. 一份文件同時服務三種讀者，交付前自問是否都填滿：工程／client（元件清單與規則）、美術（各畫面右欄的圖）、客服／玩家（說明頁）。
5. 語氣正式中帶口語，不過度包裝。
6. 複雜度判斷：新建且多條獨立流程才委派 subagent 並行萃取節點清單；調整模式不委派。
